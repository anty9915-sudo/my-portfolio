## 1. 관리자 인증 방식

### 1.1 전제

- 관리자는 1명, 회원가입 없음.
- 프론트엔드와 백엔드가 분리된 REST API 구조 (`CLAUDE.md` 2.1).
- 프론트엔드 프레임워크와 배포 도메인은 아직 미정.

### 1.2 후보 비교

| 방식 | 장점 | 단점 | 평가 |
| --- | --- | --- | --- |
| **A. 서버 세션 + HttpOnly 쿠키 (MongoDB 세션 저장)** | 로그아웃·비밀번호 변경 시 즉시 무효화, JS에서 토큰 접근 불가(XSS 시 탈취 어려움), 구현 단순 | 세션 저장소 필요, 쿠키 기반이라 CSRF 방어 필요, 교차 사이트 배포 시 쿠키 제약 | **권장** |
| B. JWT (HttpOnly 쿠키 저장) | 서버 저장소 불필요 | 즉시 폐기가 어려워 결국 블랙리스트·리프레시 토큰 저장이 필요 → 단일 관리자에게 과한 복잡도 | 대안 |
| C. JWT (localStorage 저장) | 구현 쉬움, CSRF 무관 | XSS 한 번이면 토큰 탈취, 폐기 어려움 | 비추천 |
| D. HTTP Basic 인증 | 가장 단순 | 로그아웃 불가, 매 요청 비밀번호 전송, 잠금 정책 적용 어려움 | 비추천 |
| E. GitHub OAuth 로그인 (본인 계정만 허용) | 비밀번호 저장 없음, GitHub 2FA 활용 | OAuth 앱 등록·콜백 처리, 외부 의존, 결국 세션은 필요 | 2단계 대안 |

### 1.3 권장안: A. 서버 세션 + HttpOnly 쿠키

**선택 이유**

1. **즉시 폐기**: 세션을 서버에서 지우면 바로 무효가 된다. 단일 관리자 시스템에서 JWT의 "무상태" 장점은 거의 의미가 없다.
2. **XSS 피해 축소**: HttpOnly 쿠키는 스크립트로 읽을 수 없다. 학습 기록의 Markdown 렌더링처럼 XSS 위험이 있는 기능이 있으므로 중요하다.
3. **단순성**: 리프레시 토큰 회전, 토큰 블랙리스트 등이 필요 없다.
4. **학습 가치**: 세션, 쿠키 속성, CSRF 방어를 직접 설계하는 과정이 웹 보안 포트폴리오로서 의미가 있다.

**세부 설계 (제안)**

| 항목 | 내용 |
| --- | --- |
| 비밀번호 해시 | **Argon2id (기본안)**. `argon2` 패키지는 네이티브 바이너리를 사용하므로 Node v24.16.0 + Windows에서 설치 확인 필요, 실패 시 bcrypt (cost 12 이상) |
| 세션 저장 | MongoDB `sessions` 컬렉션 (TTL). 저장 데이터는 `adminId`, `loginAt`만 |
| 쿠키 | 운영 `__Host-sid`, `HttpOnly; Secure; SameSite=Lax; Path=/` |
| 만료 | 유휴 2시간(요청마다 연장), 절대 만료 12시간 (`loginAt` 기준 검사) |
| 세션 고정 방지 | 로그인 성공 시 세션 ID 재발급 |
| 무효화 | 로그아웃 시 삭제. 비밀번호 변경 시 현재 세션은 재발급(`loginAt` 갱신)하고 나머지는 삭제. `loginAt`이 `passwordChangedAt`보다 이전인 세션 거부 |
| 무차별 대입 방어 | IP당 15분 10회 + 계정 연속 5회 실패 시 15분 잠금 |
| CSRF | `SameSite=Lax` + `/api/v1`의 모든 비-GET 요청에 `Origin` 검증(불일치·누락 시 403) + 본문 있는 요청의 JSON Content-Type 강제. CSRF 토큰은 1단계에서 사용하지 않음 |
| 계정 생성 | 회원가입 API 없음. 초기화 스크립트로 1회 생성 |
| 2단계 인증 | 미정 (TOTP는 2단계 후보) |

**알려진 한계**

- 계정 잠금(429 `TOO_MANY_ATTEMPTS`)은 실제 존재하는 이메일에만 발생하므로, 공격자가 관리자 이메일의 존재를 추정할 수 있다. 관리자가 1명이고 이메일 노출의 영향이 작아 허용 가능한 위험으로 판단한다. 엄격히 막으려면 존재하지 않는 이메일에도 메모리상 실패 카운터를 적용한다.
- **배포 도메인에 따라 쿠키 설정이 달라진다** (6장 미정 사항 U-01). 프론트엔드와 API가 서로 다른 사이트(예: `*.vercel.app`과 `*.onrender.com`)이면 `SameSite=None`이 필요하고, 브라우저의 서드파티 쿠키 차단으로 로그인이 동작하지 않을 수 있다. 같은 사이트(예: `example.com` + `api.example.com`) 또는 프론트엔드 호스트의 `/api` 리버스 프록시 구성을 권장한다.

## 2. 방문 통계의 중복 집계 기준

### 2.1 용어 정의 (제안)

| 지표 | 정의 |
| --- | --- |
| 페이지뷰 | 프론트엔드가 라우트 진입 시 보낸 `POST /visits` 중 아래 제외·중복 규칙을 통과한 건 |
| 방문자 식별값 (`visitorHash`) | `HMAC-SHA256(일별 키, IP + User-Agent)`. 서버에서 계산 후 IP·UA 원문은 버림 |
| 일별 고유 방문자 | 하루(KST) 동안의 서로 다른 `visitorHash` 수 |
| 기간 고유 방문자 | **제공하지 않음**. 대신 "일별 고유 방문자 합계"를 제공 |

### 2.2 중복 제거 규칙

| 규칙 | 기준 | 구현 |
| --- | --- | --- |
| 같은 방문자가 같은 경로를 30분 내 다시 조회 (새로고침, 뒤로 가기 반복) | 1회만 집계 | `dedupKey = SHA-256(visitorHash + path + floor(Unix 시각(분) / 30))`에 unique 인덱스. 중복 삽입 오류는 무시 |
| 같은 방문자가 다른 경로 조회 | 각각 집계 | 경로가 다르면 `dedupKey`가 다름 |
| 같은 방문자의 다음 날 방문 | 새 방문자로 집계 | 일별 키가 바뀌어 `visitorHash`가 달라짐 (의도된 동작) |

- 30분 구간은 고정 구간(00~29분, 30~59분)이라, 경계를 걸친 새로고침(예: 10:29 → 10:31)은 2회 집계될 수 있다. 개인 포트폴리오 규모에서 허용 가능한 오차로 판단한다.
- 대안: 최근 30분 내 같은 방문자·경로 기록이 있는지 조회 후 삽입 — 더 정확하지만 경쟁 조건이 생기고 쿼리가 1회 늘어난다.

### 2.3 집계 제외 대상

- 관리자 세션이 있는 요청 (관리자 본인의 조회)
- User-Agent가 비어 있거나 봇 패턴과 일치하는 요청 (6단계 정의: `bot`, `crawl`, `spider`, `slurp`, `scrap`, `headless`, `phantomjs`, `lighthouse`, `pagespeed`, `pingdom`, `uptime`, `monitor`, `preview`, `facebookexternalhit`, `embedly`, `curl`, `wget`, `python-requests`, `python-urllib`, `httpclient`, `okhttp`, `axios`, `node-fetch`, `undici`, `go-http-client`, `java/`, `libwww`, `postman` — 대소문자 무시, `src/modules/visits/userAgent.js`)
- `Sec-Purpose: prefetch` / `Purpose: prefetch` 헤더가 있는 요청
- 검증 실패 요청 (400), 빈도 제한 초과 요청 (429)

### 2.4 일별 키 관리 방식 — **기본안: A**

| 방식 | 장점 | 단점 |
| --- | --- | --- |
| **A. `HMAC(VISIT_HASH_SECRET, dateKey)`로 일별 키 파생 (권장)** | 서버 재시작에도 같은 날 같은 키 유지, 추가 저장소 불필요 | 비밀키가 유출되면 IPv4 전수 대입으로 과거 해시와 IP를 대조할 가능성 → 90일 TTL과 키 교체로 완화 |
| B. 매일 무작위 키 생성, DB에 당일분만 보관 후 삭제 | 지난 키가 남지 않아 사후 대조 불가 (프라이버시 강함) | 키 저장·회전 로직 추가, 재시작·다중 인스턴스 고려 필요 |

### 2.5 알려진 한계

- 같은 공유기·회사망(NAT)과 같은 브라우저를 쓰는 서로 다른 사람은 1명으로 집계될 수 있다 (과소 집계).
- 같은 사람이 와이파이 ↔ 모바일 데이터를 오가거나 브라우저가 업데이트되면 2명으로 집계될 수 있다 (과대 집계).
- 광고 차단기가 `/visits` 요청을 막으면 집계되지 않는다.
- 이 수치는 **추세 파악용**이며, 정확한 방문자 수를 보장하지 않는다는 점을 대시보드에 표시하는 것을 권장한다.
- (6단계 확인) 30분 고정 구간 경계를 걸친 새로고침은 2회 집계된다. iPadOS Safari는 데스크톱 UA를 보내 `desktop`으로 분류된다. `TRUST_PROXY`가 틀리면 모든 방문자가 프록시 IP 하나로 보여 크게 과소 집계된다. 관리자 제외는 프론트엔드가 `credentials: 'include'`로 요청할 때만 동작한다.
- (6단계 확인) 중복 제거·90일 자동 삭제·일별 문서 단일성은 각각 `dedupKey_unique`·`visit_events_ttl`·`dateKey_unique` 인덱스에 의존한다. 운영 DB에 인덱스를 동기화하기 전에는 보장되지 않는다.

### 2.6 채택하지 않은 대안

| 대안 | 채택하지 않은 이유 |
| --- | --- |
| 쿠키·localStorage 기반 방문자 ID | 기간 고유 방문자는 정확해지지만, 기기 식별자를 저장하게 되어 쿠키 동의 배너와 개인정보 처리방침 범위가 커진다 |
| Google Analytics 등 외부 분석 도구 | 서드파티 스크립트·쿠키 사용, "직접 구현한 통계 대시보드"라는 기능 목표와 맞지 않음 |
| IP 원문 저장 | 개인정보 최소 수집 원칙 위반 |

## 3. 문의 폼 스팸 방지

### 3.1 다층 방어 (1단계 제안)

| 층 | 방식 | 막는 대상 | 사용자 불편 | 상태 |
| --- | --- | --- | --- | --- |
| 1 | 허니팟 필드 `website` (화면에 숨김, `tabindex=-1`, `autocomplete=off`) | 모든 입력란을 채우는 단순 봇 | 없음 | 제안 |
| 2 | 서명된 폼 토큰 (발급 후 3초 이상, 1시간 이내 제출) | 폼을 거치지 않는 직접 POST, 즉시 제출 봇 | 없음 | 제안 |
| 3 | IP 빈도 제한 (10분 3회, 24시간 10회) | 대량 제출 | 거의 없음 | 제안 |
| 4 | 내용 검사 (메시지 10~3,000자, URL 4개 이상 거부) | 링크 스팸 | 낮음 | 제안 |
| 5 | 24시간 내 동일 내용(`contentHash`) 중복 제출 무시 | 반복 제출, 실수로 인한 중복 | 없음 | 제안 |
| 6 | CORS + `Origin` 검증 | 다른 사이트에서의 브라우저 기반 제출 | 없음 | 제안 |

- 1·2·5번에 걸린 요청은 **정상 응답(202)과 같은 응답**을 반환하고 저장만 하지 않는다. 봇이 차단 규칙을 학습하지 못하게 하기 위함이다.
- 차단 건수는 로그에 사유별 카운트만 남기고, 제출 내용은 남기지 않는다.

### 3.2 2단계 대안 (스팸이 실제로 늘어날 경우)

| 대안 | 장점 | 단점 |
| --- | --- | --- |
| Cloudflare Turnstile | 무료, 대부분 사용자에게 퍼즐 없음 | 외부 스크립트, 서버 측 검증 API 호출 필요, 개인정보 처리방침에 명시 필요 |
| hCaptcha / reCAPTCHA | 효과 검증됨 | 사용자 불편, 외부 추적 우려 |
| 이메일 알림 대신 관리자 화면에서만 확인 | 스팸이 메일함을 채우지 않음 | — (1단계 기본값) |

### 3.3 문의 접수 알림

- 새 문의를 이메일로 알리는 기능은 **범위 밖(미정)**이다. 메일 발송 서비스와 API 키가 추가로 필요하다. 1단계는 관리자 대시보드에서 `status=new` 개수로 확인한다.

## 4. 다크 모드의 클라이언트 상태 관리

### 4.1 원칙

- 다크 모드는 **순수 클라이언트 기능**이다. 서버 API, DB 필드, 쿠키를 사용하지 않는다 (제안).
- 프론트엔드 프레임워크가 미정이므로, 프레임워크와 무관한 규칙만 정한다. 구체적 구현은 Pen 디자인 확정 후 결정한다.

### 4.2 상태 모델 (제안)

| 항목 | 내용 |
| --- | --- |
| 사용자 선택값 | `light` \| `dark` \| `system` (기본값 `system`) |
| 실제 적용값 | `light` \| `dark` — `system`이면 `prefers-color-scheme` 결과 |
| 저장 위치 | `localStorage` 키 `theme` (예외 발생 시 저장 없이 동작 — 사생활 보호 모드 대비) |
| 단일 출처 | `<html data-theme="dark">` 속성. CSS는 이 속성과 CSS 변수로 색상을 전환 |
| 깜빡임 방지 | `<head>`의 작은 인라인 스크립트가 첫 렌더링 전에 `data-theme`를 설정 |
| 시스템 설정 변경 | `system` 선택 시 `matchMedia('(prefers-color-scheme: dark)')` 변경 이벤트를 구독 |
| 브라우저 기본 UI | CSS `color-scheme` 속성으로 스크롤바·폼 컨트롤 색상도 맞춤 |
| 접근성 | 전환 버튼에 현재 상태를 알리는 `aria-label`, 두 테마 모두 WCAG AA 대비 충족 |

### 4.3 서버 측 저장을 하지 않는 이유

- 방문자는 로그인하지 않으므로 서버에 사용자별 설정을 저장할 주체가 없다.
- 관리자 1명의 설정을 위해 DB 필드를 두는 것은 이익이 작다.

### 4.4 미정

- 프론트엔드가 SSR(서버 렌더링)을 사용하게 되면, 서버가 첫 HTML에서 테마를 알 수 있도록 쿠키 저장이 필요할 수 있다 (U-08).

## 5. 개인정보 최소 수집 및 보관 정책

### 5.1 수집 항목 (제안)

| 대상 | 수집 항목 | 목적 | 보관 기간 | 수집하지 않는 항목 |
| --- | --- | --- | --- | --- |
| 문의자 | 이름(닉네임 가능), 이메일, 제목(선택), 문의 내용, 동의 버전·시각 | 문의 확인 및 회신 | 접수 후 180일 (미정) | IP, User-Agent, 전화번호, 첨부파일 |
| 방문자 | 경로, 외부 유입 호스트명, 기기 유형, 일별 회전 해시 | 방문 추세 파악 | 원본 90일, 비식별 집계 영구 | IP 원문, UA 원문, 쿠키 ID, 위치 |
| 관리자 | 이메일, 비밀번호 해시, 마지막 로그인 시각 | 인증 | 계정 존재 기간 | 로그인 IP·기기 기록 |

### 5.2 필요한 후속 작업

- 문의 폼 화면에 **개인정보 수집·이용 동의** 문구(수집 항목, 목적, 보관 기간, 동의 거부 권리)와 체크박스를 표시한다. 문구 버전은 `consentVersion`으로 관리한다.
- 프론트엔드에 **개인정보 처리방침** 페이지를 둔다 (방문 통계 수집 방식 포함). 문구는 미정.
- 문의자가 삭제를 요청하면 `DELETE /admin/inquiries/:id`로 즉시 삭제한다.
- 개인 포트폴리오에 개인정보 보호법의 어떤 의무가 적용되는지는 별도 확인이 필요하다 (U-10). 이 설계는 적용 여부와 관계없이 최소 수집 원칙을 따른다.

### 5.3 기술적 보호 조치 (제안)

- 개인정보가 담긴 컬렉션(`inquiries`)은 TTL로 자동 파기한다.
- 애플리케이션 로그에 이메일, 문의 본문, 비밀번호, 세션 ID를 남기지 않는다.
- Atlas 접근은 최소 권한 DB 사용자와 IP 접근 목록으로 제한한다 (`CLAUDE.md` 5.1).
- 백업에는 `inquiries`, `visit_events`를 포함하지 않는다.
